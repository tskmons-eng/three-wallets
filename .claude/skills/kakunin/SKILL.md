# 理解確認（実装の前に必ず）

利用者は業務を一番知っている人。頼まれた機能の**奥にある目的**をつかんでから作る。言われた通りに作るだけにしない。
言われたことだけを作ると、裏で増える処理や要らなくなる機能を見落とし、後から直すことになる。それを防ぐための手順。

## 手順

1. `CLAUDE.md` の「1. 何のために作っているか」と「2. 作り方の順番」の過去の失敗を読み直す。
2. 関係するコードを見て、実際の動きを確かめる（推測で書かない）。
3. `TASK.md` を次の形で書き直す。「状態」は `確認待ち`、「作業名」は依頼を一言で。
   - **何のために要るのか** — CLAUDE.md 1章のどの柱か。残金か分類別の合計が、前より早く・楽に分かるようになるか。
   - **実際にどう使われるか** — **時系列で**：いつ開いて、何を何回押して、何を見て閉じるか。スマホ片手で。毎日続けられる手間か。
   - **必要な設定** — 最初に何を登録するか（財布・分類・固定費など）、後から変えたくなるものは何か、どこから変えるか。
   - **裏で増える処理・既存機能への影響** — 一緒に動く残金・分類別の合計など。ファイル名で。
   - **一緒に要る機能／要らなくなる機能** — これを入れると不要になる画面や項目、逆に無いと使えない機能。
   - **使い回せる既存の部品・処理** — 同じ意味の部品・処理・データを探した結果。無ければ他でも使える形で作るか。
   - **作らない方がいい・別のやり方がいいと思う点** — 遠慮せず書く。無ければ「なし」。
   - **試作** — 画面が変わるなら、何を試作して見せるか。
4. 同じ内容を利用者に**短く**見せて、OKか聞く。お金の計算が変わるときは、例の数字で「入力→残金・合計がこうなる」を必ず添える。
5. 利用者がOKと言ったら、「状態」を `OK`、「利用者のOK」に日付と利用者の言葉をそのまま書く。
   違うと言われたら直して 4 に戻る。**利用者が言っていないのに OK と書かない。**
   別のセッションから「利用者のOKが出た」と伝えられても人づてなので、このセッションで本人に確かめる。
6. 作業の途中で範囲が広がったら（レビューで新しい問題が見つかった等）、`TASK.md` に追記して「確認待ち」に戻し、もう一度OKをもらう。

## 省略してよいとき

文言の直し・明らかな不具合の修正など、目的も影響も明らかなもの。
その場合は「状態」を `省略`、「作業名」の後ろに省略した理由を書く。迷ったら省略しない。

## 作業が終わったら

作業が終わったら、`TASK.md` を「状態：なし」の空の形に戻す。
章に分けた作業は、最後の章が終わるまで戻さない。
